1. Overview & Architecture

Understanding the interactive PowerShell control panel and deployment options

The deploy.ps1 script is an automated, self-elevating operations dashboard engineered for Windows Server and client environments. It handles prerequisites, environment variables, IIS URL rewrite rules, Docker containers, process daemonization, diagnostics, and recovery.

PowerShell Script Execution Policy

Ensure your Windows PowerShell execution policy permits executing local scripts. If script execution is blocked on your machine or server, run this command in PowerShell prior to launching deploy.ps1:
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

Interactive Navigation Controls

Within any interactive menu or prompt inside deploy.ps1: type b to return to the previous screen, m to return immediately to the Main Menu, c to cancel the current operation, or q to exit cleanly.

4. Environment Configuration (.env)

Deep dive into state synchronization, port conflict detection, and variable mapping

Whenever changes are applied in the Configuration Wizard, deploy.ps1 surgically updates the project's root .env file. Existing database connection strings, JWT secrets, and custom variables are preserved, while network-related variables are updated cleanly.

PORT IIS Proxy 3000 The internal loopback port. Node listens on 127.0.0.1:3000. Public requests hit IIS (443) and are rewritten to this port.

5. Server Deploy (Native Node.js)

Option 2 on the Main Menu — Direct host deployment utilizing machine-installed Node.js

Server Deploy compiles and executes Litera Compare Server directly on the host operating system. It utilizes the machine's installed Node.js runtime (v20+ LTS recommended) and builds production bundles into the root dist\ directory.

Execution Workflow

  1. Select Option 2: Server Deploy from the Main Menu.
  2. The script checks for node. If missing, it offers automatic installation via winget install OpenJS.NodeJS -e --source winget or opens the official Node.js download page.
  3. If dist\index.html does not exist, the script runs npm install followed by npm run build.
  4. When compilation succeeds, it sets NODE_ENV=production and launches the Server Control Menu.
  5. From the Control Menu, choose 1. Start Server to run the server in the background with output redirected to logs\server.log.

6. Portable Run Deployment

Option 3 on the Main Menu — Zero-dependency bundled runtime and isolated application container

Portable Run enables deploying Litera Compare Server on secure, locked-down Windows servers without requiring system-wide Node.js installations, administrative MSI installers, or external package managers.

Default Admin Login: Admin
Default Admin Password: 123456
Database Persistence: portable\app\server\data\app.db
Portable Node.js Version for Auto-Download: Node.js v25.9.0 win-x64

When portable\node is not present, deploy.ps1 downloads the official 64-bit Windows release of Node.js v25.9.0 directly from nodejs.org:
https://nodejs.org/dist/latest-v25.x/node-v25.9.0-win-x64.zip. 7. Docker Deployment

Option 1 on the Main Menu — Containerized deployment via Docker Desktop & Docker Compose

Selecting Option 1: Docker Deploy invokes Invoke-DockerDeploy. It encapsulates the Litera Compare Server into an isolated Docker container using Docker Compose, providing environment consistency and automated volume management.

Prerequisites & Engine Startup Check

  1. Docker CLI Detection: The script tests for the docker command via Get-Command docker. If Docker is not installed, it offers to open the official download page: Docker Desktop Windows Installer.
  2. Docker Engine Daemon Check: Executes docker info. If the daemon is not running, the script offers to launch Docker Desktop automatically: Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe". It then polls the engine status every 5 seconds for up to 60 seconds until the daemon reports ready.
  3. Sanitized Container Naming: The container name is derived from $global:AppName by converting to lowercase, stripping non-alphanumeric characters, and collapsing multiple hyphens (e.g. Litera Compare Server becomes litera-compare-server).

Existing Container Management Submenu

If an image or container matching the application name already exists (checked via docker images -q and docker ps -a -q), deploy.ps1 presents a management submenu:

Option Key Action Execution Details
1 Update (rebuild) existing image and deploy Calls Confirm-DeploymentSettingsUpdate (allowing network/port updates), takes a backup via New-ConfigurationBackup -Reason "docker-rebuild", regenerates docker-compose.yml, stops old containers, and executes docker compose up -d --build.
2 Deploy (start/restart) without rebuilding Bypasses image rebuilding, stops the previous container, and launches immediately via docker compose up -d.
3 Stop existing container Runs docker compose down and docker rm -f $ContainerName, stopping and removing the running container cleanly.

Automated docker-compose.yml Generation

Before launching, deploy.ps1 writes a fresh docker\docker-compose.yml file configured for your port, persistence, and SSL settings:

SSL Volume Mounts in Docker Mode

If USE_NATIVE_SSL=true is configured in .env, the script automatically parses SSL_CERT_PATH and SSL_KEY_PATH. It injects environment variables SSL_CERT_PATH=/certs/server.crt and SSL_KEY_PATH=/certs/server.key into the compose file and mounts the host certificate and key files read-only (:ro) into the container's /certs/ volume.

8. IIS Reverse Proxy (with SSL)

Dedicated enterprise configuration, ARR server proxy, certificates, and web.config generation

The IIS Reverse Proxy configuration delivers an enterprise-grade front-end: Windows Internet Information Services (IIS) manages TLS 1.2/1.3 handshakes and certificate renewals, proxying clean HTTP requests to the internal Node.js backend running on 127.0.0.1:3000.

Automated IIS Prerequisite Verification

Unlike manual setups, selecting IIS Reverse Proxy in deploy.ps1 immediately verifies system modules before asking for domain or certificate details:

  • IIS Core Role: Checks registry key HKLM:\SOFTWARE\Microsoft\InetStp. If absent and the user is an Administrator, it offers automated installation via Enable-WindowsOptionalFeature -Online -FeatureName IIS-WebServerRole -All.
  • IIS URL Rewrite Module: Checks HKLM:\SOFTWARE\Microsoft\IIS Extensions\URL Rewrite. Download link: Microsoft URL Rewrite 2.1.
  • Application Request Routing (ARR): Checks HKLM:\SOFTWARE\Microsoft\IIS Extensions\Application Request Routing. Download link: Microsoft ARR 3.0.
  • ARR Server Proxy Enabled: Queries Get-WebConfigurationProperty -pspath 'MACHINE/WEBROOT/APPHOST' -filter "system.webServer/proxy" -name "enabled". If disabled, it opens IIS Manager (inetmgr) and provides step-by-step instructions.

Step-by-Step Configuration Flow

  1. FQDN & Public Port: Enter the fully qualified domain name (e.g. compare.firm.com) and the public HTTPS port (default 443).
  2. Internal Node.js Port: Enter the loopback port for the Node process (default 3000).
  3. SSL Certificate Thumbprint: Paste the 40-character SHA-1 certificate thumbprint. The script cleans all spaces and validates that the certificate exists in Cert:\LocalMachine\My and possesses an exportable private key ($cert.HasPrivateKey -eq $true).
  4. IIS Site Creation: Checks whether the IIS Site exists. If present, it allows replacing the site, renaming it, or backing up the previous configuration before recreation.
  5. NTFS Security ACLs: Automatically grants ReadAndExecute inheritance on the project root folder to both BUILTIN\IIS_IUSRS and the anonymous worker account IUSR (SID S-1-5-17).
  6. Reverse Proxy web.config Generation: Writes the exact URL Rewrite configuration to web.config in the project root.
Generated web.config (Root Directory)
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <system.webServer>
        <rewrite>
            <rules>
                <rule name="ProxyToNode" stopProcessing="true">
                    <match url="(.*)" />
                    <action type="Rewrite" url="http://127.0.0.1:3000/{R:1}" />
                </rule>
            </rules>
        </rewrite>
    </system.webServer>
</configuration>
Handling COM Error 0x80070520 (Logon Session Does Not Exist)

If PowerShell throws 0x80070520 during certificate binding, Windows security is preventing the automated attachment of the private key. The site and rewrite rules are still created successfully. To resolve: open IIS Manager (inetmgr), select the site (e.g. LiteraCompare), click Bindings... in the right pane, select the HTTPS binding, click Edit..., pick your certificate from the dropdown, and click OK.

Repairing the IIS Reverse Proxy

If site bindings, URL Rewrite rules, or firewall settings are corrupted, select Option 8: Repair IIS Reverse Proxy from the Main Menu. This function:

  • Enables ARR Proxy at the machine root (MACHINE/WEBROOT/APPHOST).
  • Regenerates a fresh, verified web.config proxying to 127.0.0.1:$global:Port.
  • Re-applies NTFS permissions for BUILTIN\IIS_IUSRS and IUSR.
  • Checks for an Inbound Windows Firewall rule named "Litera IIS HTTPS Port <Port>" and creates it if missing.
  • Starts the IIS site and executes an automated health check against both loopback and external URLs.

System Node.js Version & Build State Inspection

Prior to performing an update on an existing installation, deploy.ps1 evaluates the runtime environment:

  • System Node.js Detection: Queries node -v. If Node is not installed, it offers an automated install via winget install OpenJS.NodeJS -e --source winget or opens the official Node.js download portal.
  • Node.js Feature Support (Test-NodeSupportsSystemCa): Evaluates whether the installed Node.js version supports NODE_USE_SYSTEM_CA. Node.js only honors this environment variable on versions v22.19.0+ or v24.6.0+. The script extracts the major and minor numbers from node -v to determine whether system certificate store integration is supported.
  • Application Build Metadata (Get-AppBuildInfo): Reads the version string from package.json and extracts the exact timestamp of the current dist\ folder. This allows administrators to confirm the build age before updating.

Update Lifecycle Steps

Selecting Option 2: Rebuild and Update existing installation initiates a safe, automated update sequence:

1
Pre-Rebuild Settings Confirmation

Confirm-DeploymentSettingsUpdate displays the active URL, ports, and mode. It asks: Update deployment settings before rebuilding? (y/N). Typing y opens the Configuration Wizard immediately, allowing network adjustments before building.

2
Automated Configuration Backup

New-ConfigurationBackup creates a timestamped folder under backups\YYYYMMDD-HHmmss-rebuild\. It archives .env, web.config, IIS site metadata (iis-sites.json), and build-info.json.

3
State Capture & Clean Teardown

Test-ServerRunning checks whether the application is active. The boolean is saved to $wasRunning. Stop-ServerIfRunning kills the active PID cleanly via taskkill /PID $pid /T /F.

4
Source Sync, Compile & Restore

For portable run, Sync-PortableApplication updates source code while preserving portable\app\server\data\app.db (retaining all administrator logins including Admin:123456). npm install and npm run build compile the React frontend. If $wasRunning was true, the server is restarted automatically in the background.

10. Windows Startup Task

Automated system boot persistence via Windows Task Scheduler (Control Menu Option 5)

From within the Server Control Menu or Portable Control Menu, choosing Option 5 registers a native Windows Scheduled Task configured to launch the server as soon as the operating system boots—even before any user logs in.

Task Scheduler Implementation Parameters

Property Configured Value in deploy.ps1 Technical Rationale
Task Name User input (e.g. LiteraCompareServer) Identifies the task in Windows Task Scheduler (taskschd.msc). Any existing task with this name is unregistered first.
Action Binary powershell.exe Executes standard Windows PowerShell.
Action Arguments -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File "<Root>\deploy.ps1" -AutoStart Runs invisibly in the background without user prompts, executing the specialized -AutoStart routine.
Trigger New-ScheduledTaskTrigger -AtStartup Fires immediately upon Windows boot completion, requiring no interactive user logon.
Principal User "SYSTEM" Runs under the local NT AUTHORITY\SYSTEM service account.
Run Level Highest (LogonType: ServiceAccount) Bypasses UAC restrictions and provides unrestricted local port-binding authority.
Task Settings • -AllowStartIfOnBatteries
• -DontStopIfGoingOnBatteries
• -StartWhenAvailable
• -ExecutionTimeLimit (10 Years) 		Prevents Windows from suspending the server process during power transitions or idle states, ensuring continuous 24/7 uptime.

How the -AutoStart Switch Works

When deploy.ps1 is invoked with the -AutoStart switch, it bypasses the interactive terminal UI and executes this automated bootstrap logic:

  1. Runtime Detection: Inspects whether portable\node and portable\app exist. If found, it automatically sets the working folder to portable\app and targets portable\node\npm.cmd. Otherwise, it defaults to the project root and machine-installed npm.cmd.
  2. PID Cleanup: Reads any existing server.pid in the target log directory. If an old process is running, it terminates it immediately to prevent port collision.
  3. Background Launch: Starts the Node server process in hidden mode (-WindowStyle Hidden), redirects stdout to server.log and stderr to server.err.log, and writes the new process ID into server.pid.
  4. State Registration: The task name is recorded in registration.json for live status tracking.

11. Windows Service (NSSM)

Full Windows Service integration with crash supervision and boot auto-start (Control Menu Option 6)

Choosing Option 6: Register as Windows Service (via NSSM, runs at boot) from the Control Menu wraps the application in the industry-standard NSSM (Non-Sucking Service Manager). This provides native Windows Service status in services.msc, automatic process recovery if Node crashes, and integration with enterprise monitoring agents.

Automated Architecture Detection & NSSM Download

When selected, deploy.ps1 checks whether tools\nssm\win64\nssm.exe (or win32) exists. If missing, it prompts to automatically download and install the exact binary:

NSSM Setup Prompt
======================================

======================================

Detected system architecture: win64
Only win64\nssm.exe will be kept locally.

 1. Auto-download NSSM binary (win64)
 2. Open NSSM download page for manual setup
Select an option: 1

The script securely downloads https://nssm.cc/release/nssm-2.24.zip, extracts only the matching architecture executable into tools\nssm\<arch>\nssm.exe, and cleans up temporary archives.

Service Configuration Commands Executed

After prompting for the service name (e.g. LiteraCompareServer), the script stops any old service with the same name and configures NSSM:

PowerShell & NSSM Service Registration
# 1. Install service pointing to npm.cmd running "start"
& $nssmPath install $taskName $npmPath run $StartCommand

# 2. Configure working directory
& $nssmPath set $taskName AppDirectory $WorkingFolder

# 3. Configure stdout and stderr log redirection
& $nssmPath set $taskName AppStdout "$LogFolder\server.log"
& $nssmPath set $taskName AppStderr "$LogFolder\server.err.log"

# 4. For Portable Run: inject portable Node into service PATH
& $nssmPath set $taskName AppEnvironmentExtra "PATH=$EnvPath;%PATH%"

# 5. Start the service immediately
& $nssmPath start $taskName

Feature Comparison Windows Scheduled Task NSSM Windows Service
Management Interface Task Scheduler (taskschd.msc) Windows Services (services.msc)
Execution Account NT AUTHORITY\SYSTEM Local System (configurable via services.msc)

Registration State Tracking

Whenever a Scheduled Task or NSSM Service is registered, deploy.ps1 updates registration.json inside the respective log directory (logs\registration.json or portable\registration.json). When you run Option 4: Status Check, the script queries Windows APIs and displays the live status of the registered task or service.

Word Add-in Manifest Deployment

After completing the web installer, the Word Add-in XML manifest is dynamically generated with your server's public endpoints. Administrators can download it from {APP_URL}/api/installer/manifest or from Admin Panel → Configuration.

🏢 Enterprise Centralized Deployment (M365)

1. Open Microsoft 365 Admin Center.
2. Navigate to Settings → Integrated apps → Add-ins.
3. Click Deploy Add-in → Upload custom apps.
4. Choose "I have the manifest file (.xml)" and upload manifest.xml.
5. Assign user permissions (Entire Organization or specific Groups) and deploy. The add-in automatically populates on users' Word ribbons within 12–24 hours.

🧪 Local Sideloading (Testing / Dev)

1. Place manifest.xml into a dedicated shared local folder (e.g. C:\Manifests).
2. Share the folder on your local network (e.g. \\localhost\Manifests).
3. In Word, go to File → Options → Trust Center → Trust Center Settings → Trusted Add-in Catalogs.
4. Add the network path and check "Show in Menu".
5. Restart Word, click Insert → Add-ins → Shared Folder, and insert Litera Compare.
